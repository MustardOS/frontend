Implementation specification

Network Play &
RetroAchievements

A production-safe plan for bringing responsive multiplayer and a complete achievements experience to Pickles while preserving the performance-first character of MustardOS.

Status: Proposed Version 1.0 1 August 2026 Product + Engineering Pickles

01 — Executive overview

Two connected features, one performance budget

Network Play and RetroAchievements will be implemented as independent, opt-in subsystems over shared asynchronous networking, content identity, state capture and feature-arbitration foundations. Routine network, HTTP and image work must never block emulation, audio, video or LVGL.

N

Network Play

Up to four Pickles players over LAN discovery or direct address, with encrypted pairing, adaptive rollback and safe fixed-delay fallback.

A

RetroAchievements

A full themed experience using the official rcheevos client: identification, badges, progress, leaderboards, Softcore and validated Hardcore.

P

Performance first

Bounded queues, reusable state buffers, measured rollback eligibility and zero frame-time regression when the features are disabled.

Release principle Unsupported or expensive core/content combinations fall back clearly or decline the feature. They never jeopardise normal gameplay quality to make a compatibility claim.

04 — Shared architecture

Keep slow work away from the frame loop

The existing main loop remains the sole owner of core execution and visible UI state. Dedicated workers own sockets, TLS, cURL and badge transfers, communicating through bounded queues with explicit shutdown.

Shared services

  • Asynchronous network and HTTP request service.
  • Content and core identity cache.
  • Reusable in-memory snapshot pool.
  • Versioned save-state envelope.
  • Feature compatibility and suspension policy.

Non-negotiable invariants

  • No core, LVGL or renderer calls from workers.
  • Every queue has byte and item limits.
  • Shutdown cancels and joins outstanding work.
  • Feature-disabled paths remain effectively free.
  • Secrets never enter normal diagnostic logs.

05 — Network Play

Secure, host-authoritative and latency aware

Transport and pairing

  • Define a bounded, endian-independent PKNP/1 frame containing message type, payload length, session identifier, sequence number and emulated frame number.
  • Use TLS 1.3 over a TCP_NODELAY connection for each peer and rate-limited UDP announcements for LAN discovery.
  • Generate ephemeral mutual certificates for every hosted session. Derive the displayed six-digit code from both certificates and nonces.
  • Transmit no state or input until both devices confirm the matching code and the host approves the player.
  • Reject oversized, stale, unauthorised or structurally invalid messages before allocation or state mutation.
Security boundary Discovery announces only the host label, protocol version, connection port and available slots. It never publishes pairing material, content paths, account details or save data.

Input and rollback

  • The host owns the canonical timeline, player-to-port assignments, pause, restart, reset, disc changes and resynchronisation.
  • Each player owns one exclusive emulated port. Shared-input and spectator modes are deferred.
  • Transmit final post-mapping Retropad values, including analogue axes. Physical mappings, deadzones, turbo and RELISH evaluation remain local.
  • Begin at one frame of input delay with an eight-frame maximum rollback window.
  • Cap the rollback pool at 64 MiB by default and 128 MiB absolutely. Require space for at least two states.
  • Predict missing remote input by repeating its last confirmed value.
  • Correct from the earliest changed frame, replaying with video, audio, rumble, achievements and UI events suppressed.
  • Benchmark state capture, restore and replay before joining. Automatically use a two-to-eight-frame fixed delay if rollback would exceed the device budget.
Hardware-rendered cores Every serialise, restore and replay call uses the established hardware-context guard. Large 3D states are measured rather than assumed suitable; normal gameplay remains more important than enabling rollback.

Session integrity

  • Disable run-ahead, fast-forward, slow motion and local state loading while connected.
  • Compare canonical state digests every 60 confirmed frames.
  • Attempt one host-driven resynchronisation after a mismatch; disconnect with a clear report if it repeats.
  • Pause briefly for peer reconnection. The host chooses whether to continue with neutral input for a departed port.
  • Synchronise host pause, reset and media changes at agreed frame boundaries.
  • Support RETRO_ENVIRONMENT_GET_NETPLAY_CLIENT_INDEX and negotiate the libretro netpacket interface as a distinct core-managed mode.
  • Never combine frontend rollback with core-managed packets in the same session.

06 — RetroAchievements

Official runtime, complete MustardOS presentation

Integrate a pinned stable rcheevos release rather than reproducing achievement logic. Pickles supplies the networking, memory access, persistence and themed interface that the runtime intentionally leaves to the frontend.

Account and dependency policy

  • Vendor the official rc_client, rhash and libretro memory helper with version and MIT licence notices.
  • Provide global MustardOS settings for sign-in, sign-out, preferred mode, unofficial sets and notification visibility.
  • Use the password only for initial login, clear it immediately and persist only the returned username and token.
  • Write credentials atomically with owner-only permissions and redact them from logs.
  • Do not import, change or expose RetroArch credentials.

Content and runtime lifecycle

  1. Create one rc_client with a libretro memory reader, asynchronous server callback and validated Pickles User-Agent.
  2. Capture RETRO_ENVIRONMENT_SET_SUPPORT_ACHIEVEMENTS and copy memory descriptors supplied through RETRO_ENVIRONMENT_SET_MEMORY_MAPS.
  3. Identify content with rhash, including supported archives, playlists, CHD and disc layouts. Do not substitute the existing raw-file CRC.
  4. Hold the first emulated frame behind a responsive “Content is starting…” screen until identification completes. After ten seconds, offer Retry or Play Without Achievements.
  5. Call rc_client_do_frame after every canonical emulated frame, including non-rendered and fast-forward frames, but never after a Pickles run-ahead replay.
  6. Call rc_client_idle at least once per second while paused and notify the client on multi-disc media changes.
  7. Store rcheevos progress in new-format save states and reset hit-count progress safely after loading a legacy state.

Network and cache behaviour

  • Use asynchronous cURL requests with MustardOS proxy settings, certificate verification, redirect restrictions, size limits and explicit timeouts.
  • Complete each rcheevos server callback exactly once, including cancellation and shutdown.
  • Cache successful content identities and cap the on-disk badge cache at 64 MiB using least-recently-used eviction.
  • Decode only visible images into RAM; missing or corrupt images use a themed placeholder.
  • Follow rcheevos retry and disconnected-session semantics rather than inventing unverifiable offline unlock submissions.

Visible experience

Before play

Account status, identification progress, game placard, supported set and unlocked summary.

During play

Unlocks, measured progress, challenge indicators, leaderboard trackers and server status.

In the pause menu

Grouped achievement list, badges, points, rarity, descriptions, leaderboards and completion state.

07 — Hardcore phase

Competitive integrity without losing settings

Softcore ships first. Hardcore becomes publicly available only after compliance testing and RetroAchievements validation of the Pickles client identity and behaviour.

Temporarily suspended

  • State loading and timeline restore
  • Automatic state resume
  • Cheats and gameplay patches
  • RELISH macros and turbo
  • Slow motion and frame advance
  • Disallowed core options

Permitted with safeguards

  • Normal-speed play
  • Fast-forward
  • Creating states that cannot be loaded in Hardcore
  • Run-ahead after canonical-frame validation
  • Normal display scaling and theme UI
  • Pausing when rc_client_can_pause permits it
  • Explain restrictions, require confirmation and reset content when Hardcore begins.
  • Keep suspended values in memory without rewriting the user’s saved configuration.
  • Restore those values when Hardcore ends.
  • If a conflicting feature is selected later, pause Hardcore before applying it.
  • Keep Hardcore and all achievement processing unavailable during Network Play.

08 — Save-state compatibility

A versioned envelope with a legacy path

Existing Pickles states contain only the opaque core payload. A small envelope allows independent achievement progress and future metadata while retaining backwards compatibility.

ChunkContentsValidation
HEADPKST magic, envelope version, flags and declared lengths.Strict version, size and overflow checks.
COREOpaque bytes produced by retro_serialize.Length limit and payload integrity digest.
RACHOptional rc_client progress and hit-count state.Independent version, size and integrity check.
Future chunksLength-delimited optional data.Unknown optional chunks may be skipped safely.
  • Continue using atomic temporary-file replacement and directory synchronisation.
  • Keep screenshot sidecars unchanged.
  • Detect old raw files by the absence of PKST and pass only that payload to the core.
  • In Softcore, loading a legacy state resets achievement progress safely because exact hit counts are unavailable.
  • In Hardcore, all legacy and new state loads are rejected before reading or mutating core state.

11 — Verification

Correctness, security and frame-time acceptance

Automated protocol and rollback tests
  • Protocol encoding, bounds, malformed input, stale sequences, pairing state and compatibility manifests.
  • Deterministic fake core covering prediction, correction, four ports, pause/reset/disc events and resynchronisation.
  • Simulated latency, jitter, fragmentation, bandwidth limits, disconnect and reconnect.
  • Fuzzing of every unauthenticated discovery and pre-pairing parser.
RetroAchievements integration tests
  • Mock login, token expiry, no-game, unsupported-core, timeout, retry, malformed response and shutdown outcomes.
  • Memory maps with mirrors, offsets, disconnect masks, null ranges and fallback regions.
  • One evaluation per canonical frame during normal play, hidden rendering, fast-forward and run-ahead.
  • Legacy/new states, disc changes, corrupt badges, cache eviction and credential permissions.
  • Every Hardcore suspension and restoration path.
Target-device and performance tests
  • Representative lightweight 2D cores plus hardware-rendered SwanStation and DuckStation content.
  • Two- and four-device LAN sessions and direct-address sessions with injected latency and jitter.
  • Large states, GL context restore/replay, audio continuity, rumble suppression and colour correctness.
  • Menu responsiveness during hashing, HTTP, pairing and state transfer.
  • Four-hour soak runs with reconnects, disc changes and repeated pause/resume.
  • No measurable frame-time regression when both features are disabled.
Release acceptance
  • No unauthorised join and no persistent credential exposure.
  • No achievement submission from speculative or replayed frames.
  • No repeatable desynchronisation on combinations declared supported.
  • No regression to existing raw save-state loading.
  • No routine socket, TLS, HTTP or image work on the emulation thread.
  • Native AddressSanitizer, UndefinedBehaviourSanitizer and race-oriented checks pass.

12 — Scope boundaries and defaults

What the first release does not promise

Explicitly deferred

  • RetroArch network interoperability.
  • Public lobby, relay and managed NAT traversal.
  • Spectators and shared-input ports.
  • ROM, BIOS, patch or core transfer.
  • Voice chat, text chat and friend services.
  • Hardcore achievements during Network Play.

Default behaviour

  • Both features are independent and opt-in.
  • Network Play uses encryption and adaptive rollback where measured suitable.
  • RetroAchievements starts in Softcore.
  • Global MustardOS credentials are authoritative.
  • Achievements pause for the complete Network Play session.
  • Existing Pickles behaviour is unchanged when disabled.
